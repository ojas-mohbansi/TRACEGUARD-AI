## 1. Executive Summary

A critical objective in Phase 16 was to make the engine analytics scientifically accurate and easy to explain during a university demonstration. In prior versions, confusion arose between:
1. **Alert Attribution**: Which engine was responsible for triggering an alert?
2. **Detection Activity**: How many times did each engine evaluate or flag an anomaly across all examined network sessions?

TraceGuard AI now provides two clearly distinguished, reconciled analytical models accessible via `GET /api/alerts/engine-activity` and visualized in the main dashboard:
- **Final Alert Attribution (Mutually Exclusive)**: Partitioning every generated alert into exactly one attribution bucket (FSM-only, ML-only, Hybrid, Unknown). Sums strictly to total alerts.
- **Engine Contribution & Detection Activity (Component Activity)**: Measuring the raw diagnostic output of each individual engine. Detections may overlap when multiple engines flag the same session.

## 2. Mathematical Model & Reconciliation Formula

```
                                  +------------------------------+
                                  |     ALL NETWORK SESSIONS     |
                                  +------------------------------+
                                                 |
                       +-------------------------+-------------------------+
                       |                                                   |
                       v                                                   v
           [ FSM ENGINE EVALUATION ]                           [ ML ENGINE EVALUATION ]
           Input: Symbol sequence $w$                          Input: 15 Tabular Features
           Output: $S_{FSM} \in \{0, 100\}$                    Output: $S_{ML} \in [0, 100]$
                       |                                                   |
                       +-------------------------+-------------------------+
                                                 |
                                                 v
                                     [ HYBRID CONSENSUS ENGINE ]
                                   $S_h = 0.6 S_{FSM} + 0.4 S_{ML}$
                                  (Floor: $S_h \ge 60\%$ if $S_{FSM} = 100$)
                                                 |
               +---------------------------------+---------------------------------+
               |                                 |                                 |
               v                                 v                                 v
        [ FSM-ONLY ALERT ]                [ ML-ONLY ALERT ]               [ HYBRID CONSENSUS ]
        $S_{FSM} = 100$                   $S_{FSM} = 0$                   $S_{FSM} = 100$
        $S_{ML} < 55$                     $S_{ML} \ge 55$                 $S_{ML} \ge 55$
        attribution: "fsm"                attribution: "ml"               attribution: "hybrid"
```

### 2.1 The Two Invariants

#### Invariant 1: Final Alert Attribution is a Partition
Let $A$ be the set of all alerts generated by the system. Then:
$$A = A_{FSM} \cup A_{ML} \cup A_{Hybrid} \cup A_{Unknown}$$
where:
$$A_i \cap A_j = \emptyset \quad \forall i \neq j$$
$$|A| = |A_{FSM}| + |A_{ML}| + |A_{Hybrid}| + |A_{Unknown}|$$
The percentage shares strictly sum to $100.0\%$.

#### Invariant 2: Engine Activity Allows Component Overlap
Let $E_{FSM}, E_{ML}, E_{Hybrid}$ represent the set of sessions flagged as anomalous by each respective engine component. For any session $s$:
- $s \in E_{FSM} \iff \text{FSM violation occurs (transition into TRAP)}$
- $s \in E_{ML} \iff \text{Isolation Forest flags outlier or } S_{ML} \ge 55\%$
- $s \in E_{Hybrid} \iff s \in E_{FSM} \cap E_{ML}$ (Consensus)

Therefore, the sum of detections $|E_{FSM}| + |E_{ML}| + |E_{Hybrid}|$ naturally exceeds total alerts because sessions exhibiting both syntactic violations and statistical volume spikes are counted in both component meters.


## 4. Frontend Visualization Architecture (`Dashboard.jsx`)

In `frontend/src/pages/Dashboard.jsx`, the analytics section displays side-by-side:

### 4.1 Left Pane: Final Alert Attribution Donut Chart
- Rendered using Recharts with distinct semantic colors:
  - Cyan (`#06b6d4`): FSM Only
  - Purple (`#a855f7`): ML Only
  - Emerald (`#10b981`): Dual-Engine Hybrid Consensus
  - Slate (`#64748b`): Legacy / Unknown
- Center display reflects the total verified alert count.
- Legend displays count and exact percentage.

### 4.2 Right Pane: Engine Contribution & Detection Activity Cards
- Three dedicated cards for FSM, ML, and Hybrid:
  - **FSM Card:** Displays evaluation count, detection count, and detection rate bar. Explanatory tag: *"Protocol Violations (DFA Invariant)"*.
  - **ML Card:** Displays evaluation count, statistical detection count, and detection rate bar. Explanatory tag: *"Isolation Forest Outliers"*.
  - **Hybrid Card:** Displays consensus evaluation and high-confidence alert count. Explanatory tag: *"Dual-Engine Consensus"*.
- Callout banner explicitly clarifies the difference between mutually exclusive attribution and overlapping component evaluations.
