## 4. UI Metric Distinctions: Attribution vs Activity

TraceGuard AI presents two complementary but strictly distinguished views in the UI:

### 4.1 Final Alert Attribution (Mutually Exclusive Pie / Donut Chart)
- **Mathematical Definition**: A partition of the total alert set where each alert belongs to exactly one category:
  $$\text{Total Alerts} = N_{\text{FSM}} + N_{\text{ML}} + N_{\text{Hybrid}}$$
- **Rule**:
  - `fsm`: FSM violation detected AND ML anomaly score $< 0.55$.
  - `ml`: FSM sequence valid AND ML anomaly score $\ge 0.55$.
  - `hybrid`: FSM violation detected AND ML anomaly score $\ge 0.55$.

### 4.2 Engine Evaluation Activity (Overlapping Bar Chart)
- **Mathematical Definition**: Total component-level evaluations across the incident database:
  - FSM Evaluations: Every alert where the FSM evaluated the packet sequence.
  - ML Evaluations: Every alert where 15 features were extracted and evaluated by Isolation Forest.
  - Hybrid Consensus: Incidents where both engines contributed positive detection findings.
- **Academic Purpose**: This metric illustrates the multi-agent detection workload, showing that both engines actively evaluate traffic even when the final attribution is assigned to one specific primary engine.

## 5. Demonstration Data Isolation & Reset Capability

To avoid synthetic demonstration data contaminating live or operational telemetry:
1. **Source Labeling**: All showcase records are tagged with `[SYNTHETIC DEMONSTRATION]` in the summary string and `dataset_id = "demo_showcase"`.
2. **Dashboard Isolation**: The live-network dashboard query filters:
   ```sql
   WHERE dataset_id != 'demo_showcase' AND session_id NOT LIKE 'sess_demo_%'
   ```
3. **Reset Operation**: Calling `POST /api/detection/showcase/reset` deletes all demonstration alerts and events, instantly returning the system to clean baseline state without database drop or schema corruption.
